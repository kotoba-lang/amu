## PART 1 -- the refutation (MEASURED route fact, probe v1)

The design letter's bracket method was the COMPUTE ENCODER's
sampleCountersInBuffer:atSampleIndex:withBarrier: called before and after
the dispatch. The SDK already carries the warning (MTLComputeCommandEncoder
.h, verbatim): "On devices where MTLCounterSamplingPointAtDispatchBoundary
is unsupported, this method is not available and will generate an error if
called." The 2026-10-25 probe measured AtDispatchBoundary = 0 on this M1
Max. The harness row checked the runtime truth. It is WORSE than an error
-- the framework ASSERTS and aborts the process (probe v1 verbatim):

  device: Apple M1 Max
  sampling dispatch: 0
  sampling stage: 1
  sampling draw: 0
  sampling tile: 0
  sampling blit: 0
  sampleBuffer: OK (no error)
  -[AGXG13XFamilyComputeContext sampleCountersInBuffer:atSampleIndex:withBarrier:]:1018: failed assertion `MTLComputeCommandEncoder:sampleCountersInBuffer:atSampleIndex:withBarrier not supported on this device'
  [SIGABRT, exit 134]

The full sampling-point matrix (probe v1, five points this time -- the
2026-10-25 probe read only dispatch/stage): dispatch=0 stage=1 draw=0
tile=0 blit=0. On this device exactly ONE sampling point exists:
MTLCounterSamplingPointAtStageBoundary. The design letter's method is
therefore not merely slow or lossy here -- it is unencodable, and the
blit-encoder fallback route (AtBlitBoundary) is closed too (blit=0).

## PART 2 -- the bracket the device supports (MEASURED route fact, probe v2)

AtStageBoundary maps to the pass sample-buffer attachment indices, not to
any sampleCountersInBuffer: method (MTLComputePass.h, verbatim):

  @property startOfEncoderSampleIndex
  @abstract The sample index to use to store the sample taken at the start of
  command encoder processing. ...
  @discussion On devices where MTLCounterSamplingPointAtStageBoundary is
  unsupported, this sample index is invalid and must be set to
  MTLCounterDontSample or creation of a compute pass will fail.

  @property endOfEncoderSampleIndex   (the end-of-encoder counterpart)

Bracket DECIDED with this row (a design correction, named as such): the
counter pair brackets the dispatch by putting EXACTLY ONE dispatch inside
a compute encoder created from MTLComputePassDescriptor whose attachment 0
carries the timestamp counter sample buffer with
startOfEncoderSampleIndex=0 / endOfEncoderSampleIndex=1; the pair resolves
through the blit encoder's resolveCounters:inRange:destinationBuffer:
destinationOffset: and reads back as two MTLCounterResultTimestamp uint64
values (MTLCounters.h: `typedef struct { uint64_t timestamp; }
MTLCounterResultTimestamp`). This preserves the amendment's letter -- two
GPUTimestamp samples bracketing one reduce dispatch, delta in GPU ns --
and changes only the METHOD: the sample is taken at the encoder's
stage-boundary processing points instead of by an unencodable in-encoder
sampling call. Probe v2 verified the bracket end-to-end on this host
(verbatim, 6 trials of one 256-thread dispatch each; INSTRUMENT
VERIFICATION -- a trivial kernel, nothing reduce-shaped, no arm):

6/6 brackets resolved to two non-error uint64 samples with positive
