THE DECISION (three parts, one question: what the read licenses):

Part 1 -- DISPATCH ROWS (kotoba.compiler.accelerator-targets): NO
  MAPPING. The read does not answer a single workgroup row and no row
  moves. Four named mismatches against the rows' own channel:

  (a) ROUTE/CHANNEL: the rows are measurements OF the wire-42 loader
      path (their provenance label; ADR-0355). The read is a third
      channel even for Apple -- browser WebGPU through Chrome 155
      Dawn/Metal -- where ADR-0358's own non-claim already says the
      row's MoltenVK channel "is not a native Metal path".
  (b) WORKLOAD: the rows' channel fixes ONE workload shape (f32 ewise
      FMA); the read times reduce kernels (:sum/:max/:min) at two
      shapes. A row is chosen per the row protocol's workload, and
      the row's non-claim ("not optimality for every kernel") cuts
      against importing a different kernel family's numbers, not for
      it.
  (c) QUANTITY/PAIRING: the rows compare SIZES AGAINST EACH OTHER
      within a run (the statistic that survives host noise). The read
      pairs ARMS at FIXED W (alternating order, 11/7 rounds); its
      size ordering is derived from separate cells' medians -- one
      run, no clock/thermal regime control, by its own commit's
      words. The W sweep that IS in the read (@workgroup_size(W), W =
      32..1024) is therefore not the row statistic.
  (d) AVAILABILITY: the row channel itself cannot run today on ANY
      vendor (loader removed 2026-10-22; the per-vendor workgroup
      sweep "cannot run" until an ADR-0371 provider answers INFO). A
      row flip has no takeable channel at all right now -- the read
      is not merely the wrong channel, there is no right channel
      alive.

  Positive scope (what the read DOES license, and it is already in
  its own record): the WGSL route's first hardware timings, exact
  correctness 72/72, arm-vs-arm PARITY at wall-clock on this device,
  and the route-level W observation (batch32 argmin W=32 in 11/12
  rows, tendency not law per (3)). If that W observation were mapped
  naively onto the :apple row it would contradict the row's kept 256
  ("32-1024 medians within ~5%, no size won more than 6/16" under the
  row protocol) -- the fact that it does not GET to contradict is
  exactly what this channel rule protects.

  WHAT WOULD COUNT for a row: the ADR-0358 protocol on the row's
  channel (its ADR-0371 provider successor) -- UNMEASURED, blocked on
  the provider -- or a future decision that amends the row channel to
  a named new channel with its own within-run paired size protocol.
  The Chrome/Dawn wall-clock read is not that channel and this
  decision does not make it one. REOPEN CONDITION for part 1: a
  provider-channel or decided-new-channel row run (JUN-57..60) is new
  evidence; nothing else reopens the mapping.

Part 2 -- VARIANT CELLS (kotoba.compiler.accelerator-variants): NO
  FLIP. The claim-protocol flip needs rule 2 REGIME-INVARIANT FASTER
  at the paired medians (the cross-day standard the nine 2026-10-25
  rows reproduce: 18/18 per-run ratios below 1.0). The read is
  parity -- ratios straddle 1, the fold arm faster in a minority of
  pairs (13/36 single, 17/36 batch32 by the log's unrounded
  aggregate) -- so even inside the right channel it would flip
  nothing; and it is outside it (part 1 (a)), where "an MSL
  measurement never flips a WGSL cell" cuts symmetrically: a
  Chrome/Dawn wall-clock read never flips an MSL or GLSL cell. No
  :measured-cell record, no :shapes value and no selection answer
  moves.
