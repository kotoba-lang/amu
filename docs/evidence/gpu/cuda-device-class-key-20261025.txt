THE DECISION (this row's content -- what "narrower" is):

1. The tested device class is keyed by BOTH name fragments "xavier"
   and "agx" sitting in ONE name part (case-insensitively -- the uB5G
   per-name-part idiom of kotoba.compiler.accelerator-targets:
   evidence about a NAMED device acts on that device's name and never
   past it) AND the reported compute capability 7.2 exactly. Every
   key fails closed. This REPLACES the single fragment "xavier"
   (the same coarse key kotoba.compiler.accelerator-targets' NVIDIA
   workgroup row still uses, :measured-device "xavier" -- NOT
   narrowed here, named below).

2. The ground for the fragments is the tested device's own reported
   name: NVIDIA Jetson AGX Xavier (L4T R35.4.1, sm_72) -- the ONE
   device where the CUDA route's measurements ran (every committed
   record.txt names it: cuda-claimprotocol-run{1,2}-20261025,
   cuda-registered-sessionA-20261025). Its name carries both
   fragments; the Jetson Xavier NX name ("Jetson Xavier NX", also
   sm_72) carries "xavier" but not "agx".

3. The narrowed key names BOTH layers' records (row (iv) at its
   letter "now naming per-op records too"): ONE shared predicate
   (cuda-tested-class?) keys cuda-entry-cell (pooled) AND
   cuda-entry-op (per-op). The hole this closes: under the single
   fragment a Jetson Xavier NX descriptor read as the tested class
   and would have received every entry-contract record -- pooled AND
   per-op -- with NO measurement behind it.

4. The fragments must sit in ONE name part. The three name keys
   (:device, :name, :vendor) are alternate spellings of the device's
   name, not a fragment kit to be assembled across keys; a
   descriptor whose parts separately carry "xavier" and "agx" fails
   closed.

5. Record shape (3) is UNCHANGED: the record's :device label stays
   "xavier sm_72" byte-for-byte. What narrowed is the KEY deciding
   which descriptors ARE the class, not the record's text.

REJECTED, NAMED: (a) a negative key ("xavier" and NOT "nx") -- a
substring blacklist that only names today's known wrong answer; the
positive requirement excludes the NX without enumerating exclusions;
(b) exact-name equality -- brittle across producers' spellings
("NVIDIA Jetson AGX Xavier" vs "Jetson AGX Xavier" vs a vendor-key
spelling) and against the uB5G per-name-part idiom's tolerance; (c)
a device-id/UUID/PCI-id key -- the descriptor surface carries
:device/:name/:vendor strings and :compute-capability, no device-id
axis exists and none is invented here; it needs a producer fact that
does not exist (PROPOSED, its own row if a producer ever supplies
one); (d) narrowing kotoba.compiler.accelerator-targets' workgroup
rows' :measured-device "xavier" in the same slice -- that table's
scoping is its own decision (ADR-0355/0358), this row touches the
entry contract's class key only.

NAMED RESIDUAL, NOT HIDDEN: the key is still NAME-BASED. Any name
part carrying both fragments with a reported 7.2 still reads as the
tested class -- "Jetson AGX Xavier Industrial" (also sm_72) is the
concrete residual. It is PINNED AS BEHAVIOR by the new test (it
attaches today; pinned so the coarseness is named behavior, not an
accident) and is not a claim that anything was measured on it.
