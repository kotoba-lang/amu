# Native spawn attribute readback on three Macs

On 2026-11-04, GitHub Actions Mac job
[41787944611](https://github.com/kotoba-lang/amu/actions/runs/41787944611)
compiled the Kotoba diagnostic emitter and checked its output bytes. Its
artifact, CI log and local hash agreed on the 248-byte attribute SHA-256
`b12a84b3612e3e81416007a043b20535c6e1a70b699df37fa2146f02c632c6ec`.
The source SHA-256 was
`76ee750007f03732bb98a7dd6daef98d189c662575d81deb509e072c830c8a63`;
the emitter fixture SHA-256 was
`27ab6f932ac1407f16f3a1219f67fb75954b675c72b0a76877d414658a48a36d`.

The exact attribute bytes were sent to naphtali, benjamin and judah over
Tailscale SSH with previously pinned host keys. On each ARM64 Mac build
`25G332`, the diagnostic used those bytes in Darwin spawn syscall 244 for
one owned `/usr/bin/true`. The child was observed stopped; an independent
privileged `memorystatus_control` readback returned active/inactive limits
`[64, 1, 64, 1]`. After resume the child exited 0 and was reaped. Each
task-owned temporary directory was removed by its SSH invocation. The
target observer SHA-256 was
`e7c064de03e033ef98d56ecf9aee6cb7e2892d60f143d57f3c31866ef7dc7016`.

This confirms a single attribute-setting/readback sample per host. It does
not exercise a memory limit, GPU/unified memory, actual inference, children
or descendants, daemon containment, a scheduler, restart recovery, or a
qualified governor. No target build, model, or persistent service was run.

## Bounded enforcement and exec transition

The same CI-generated bytes were then used in serial synthetic tests on
2026-11-04. A control and a limited child each attempted to touch 128 MiB
of anonymous memory in 8 MiB reporting increments, pausing briefly between
increments and holding the completed allocation for two seconds. The parent
read memory properties independently while the child was suspended both
before interpreter execution and after the interpreter started but before
allocation. The observer was
`scripts/seed/observe-macos-attribute-enforcement.py`, SHA-256
`527fcfecca12ea019298566b89f92d7c96352fc08fee55c19d04907aad28dde8`.

On naphtali, the Command Line Tools `bin/python3.9` path returned
`[64,1,64,1]` before execution but `[-1,0,-1,0]` after interpreter startup.
Both the unlimited control and the supposedly limited process completed the
128 MiB allocation and exited 0. An earlier unpaced trial with the same
attribute also completed; it lacked the post-exec readback. Thus spawn-time
readback alone does not establish a persistent limit for this path. The
specific mechanism of the change was not identified.

On naphtali, benjamin and judah, the direct `Python.app` executable retained
`[64,1,64,1]` across the same observations. The control reported all 128 MiB
and exited 0; the limited process last reported touching 56 MiB and was
terminated by SIGKILL on each host. The kernel's kill reason was not
collected, so this is consistent with the configured limit but does not prove
the cause. Before/after system memory free indicators were 82/82%, 90/90%,
and 89/89%, respectively; swap used remained 685.75 MiB, 0, and 0. These are
non-simultaneous samples, not service-health or GPU accounting. Only owned
children and temporary directories were touched and cleaned up.

These path-specific observations do not qualify Kapitsa or any real model.
Any future host must verify limits after its final exec and cannot interpret
an unavailable or changed readback as permission to dispatch. Whole-tree
containment, durable reservations, recovery and resource governance remain
unqualified.
