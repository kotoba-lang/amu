# Linux ARM64 fixed curl signal-control diagnostic

`seed/linux-curl-sigxfsz-control-packager.kotoba` emits a 4 KiB loaderless Linux ARM64 ELF diagnostic. It marks the launcher itself non-dumpable with `prctl`, installs `SIG_IGN` for Linux `SIGXFSZ` using `rt_sigaction`, then `execve`s the fixed path `/usr/bin/curl`, forwarding the arguments with an empty environment. It exits 127 if setup or exec fails. Ignored signal disposition survives exec; dumpability can be reset at exec, so the pre-exec `prctl` does not guarantee the curl process can never dump core.

On one local Mac, an Amu native bootstrap compiled the Kotoba packager and a diagnostic FS2 host emitted the Linux ELF. In the initial revision, the emitted 150 bytes of code and fixed path matched `derivation.s` independently assembled as an ARM64 object. That assembler is a diagnostic cross-check, not an operational or build dependency of the packager. On Xavier, a temporary copy of the emitted ELF successfully ran the installed curl `--version` and was removed. The launcher is not installed and is not connected to `pr-submit`.

The bounded synthetic Unix-socket tests ran unique task-owned systemd user units on Xavier using the ELF, `LimitFSIZE=4M`, `LimitAS=128M` and `LimitCORE=0`. Before sending an oversized response, the observer held the peer response and required the observed curl process to have SIGXFSZ ignored, both file-size rlimits exactly 4 MiB, and the same PID start time before and after inspection. Otherwise it sent only a small response. A normal two-byte response completed with unit result `success`. A 4,259,840-byte response, in both Content-Length and chunked forms, produced a 4,194,304-byte output and `Result=exit-code`, `ExecMainStatus=23`, not a signal/core-dump result. Exact task units were stopped/reset as applicable and then read back `not-found` / `inactive`; peer threads finished and task directories were removed.

A negative control replaced only the `rt_sigaction` syscall instruction with `mov x0,0`, so the setup appeared to return successfully without installing SIG_IGN. The observer saw the ignored bit was absent and sent only the two-byte response. The earlier Xavier `/var/crash/_usr_bin_curl.1000.crash` report was retained; its inode, size, mtime and SHA-256 were unchanged immediately before versus after each test. This comparison is a bounded observation, not proof that no other crash report or delayed host event can occur.

This is a fixed-target diagnostic, not a production-ready supervisor, policy boundary or safe general curl execution capability. It forwards arbitrary caller arguments while clearing the environment; a trusted host must pin the executable and curl binary, restrict arguments, control inherited file descriptors, grant only intended paths and egress, handle ambiguous outcomes without replay, and qualify aggregate storage, CPU, memory and process-tree control. It does not prove safety for other architectures, kernels, curl versions, TLS, dynamic-linking environments, crash policies, or actual MTP/GitHub workloads. The file limit is per file, not an aggregate disk budget. The root workspace governor rule still blocks deployment until qualification.

## Empty-environment follow-up

The current revision passes an empty environment to `execve`. Its 146 bytes of code and fixed path matched `emptyenv-derivation.s` independently assembled as an ARM64 object. On Xavier, a task-owned transient systemd user unit supplied a synthetic marker in its environment. The observer confirmed the actual curl process had an empty environment, ignored SIGXFSZ, both 4 MiB file rlimits, and a stable PID start time before permitting the oversized synthetic response. Curl stopped at 4,194,304 bytes with `Result=exit-code`, `ExecMainStatus=23`. A small response completed successfully with the environment also empty. As a negative control, the initial launcher exposed the marker, and the observer sent only a small response. Exact task units were no longer present or active after cleanup, task directories were removed, and the previously observed crash report's inode, size, mtime and hash remained unchanged.
