Apple's [Core ML optimization overview](https://apple.github.io/coremltools/docs-guides/source/opt-overview.html) distinguishes int4/int8 weight representation from actual runtime compute. It describes M4/A17Pro Neural Engine W8A8 compute and Mac GPU per-block int4 weight opportunities, while noting that some backends decompress to float16. Thus a small stored model or an allowed compute unit cannot serve as an observed low-bit device-execution receipt.

Useful follow-on experiments are: exact CPU SIMD/range-proven narrowing first for the unchanged CPU workload; separately bounded tensor/GPU dispatch with resident buffers and transfer/synchronization costs; a Core ML adapter with observed device attribution; and explicit low-bit storage/compute/accumulator types. Exact integer narrowing must preserve overflow, sign, trap, effect and fuel semantics. Approximate model quantization needs its own error/accuracy contract and must not replace exact Embench arithmetic.

ComputeCID reuse would bind target chip/features, dtype/packing, scale/zero-point/accumulator and numeric semantics, kernel/rules, ABI/runtime/driver, shapes/strides and input dependencies. ResultCID can bind reusable kernels or deterministic results, with current-state transitions/replayed contributions separately validated. Device-dependent reductions and lossy quantization cannot be called byte-equivalent merely because their source CID matches. These are proposed extensions, not implemented persistent cache or accelerator speed claims.
