# Selfhost depthconv research: representation, unrolling and calls

The accepted fixed-workload port is generated by
`bench/embench/generate_depthconv_port.py --batch-representation table --unroll --inline-channel`
into `bench/embench/batch-ports/depthconv.kotoba`. The historical correctness
port and the generator's default output are unchanged. This is a new benchmark
implementation, not a generic compiler optimization or a full Embench score.

## Final same-run comparison

Asher, Apple M4, Apple Clang 17 `-O2`, 30 rotated samples per arm, 2,000
convolutions per call, one untimed warmup call. Each arm writes every one of
the 32 outputs and verifies once after the batch. Native arena/fuel resets
occur once per batch. Reported times include amortized verification and call
overhead. Each calibrated interval is approximately 300 ms; measured loads
must be at most 4. This load gate is not a CPU-idle qualification.

| Arm | Mean ns/convolution | Sample SD ns | Relative SD |
|---|---:|---:|---:|
| Kotoba Base64, inner loop, channel call | 3038.023 | 52.212 | 1.72% |
| Kotoba tables, four rows expanded, channel expression in kernel | 123.510 | 5.917 | 4.79% |
| Unchanged upstream C body, batch adapter | 42.582 | 1.291 | 3.03% |

The accepted port is **24.597x faster** than the matched Base64 reference
(95.93% less time), but **2.901x slower than C**. It does not meet the C-or-better
goal. The final port and reference both pass native `amu check` and `compile`.
All 32 channels match the upstream expected outputs in each arm; batch counts
1, 2, 17 and 2,000 return success. Four separate native runs confirm that
channel 32 and insufficient fuel trap in both Kotoba arms.

## Generate / Reflect / rank

Observed C code expands four multiply-accumulate rows and reads static byte
tables directly. The historical Kotoba port decodes Base64 in its inner loop.
The first candidate changes only that data representation; the next two
expand the fixed four rows and generate the channel expression in the kernel.
No expected output replaces any arithmetic. These changes exploit the pinned
benchmark profile, not arbitrary convolution shapes or inputs.

| Experiment, each measured within its own run | Reference ns | Candidate ns | Verdict |
|---|---:|---:|---|
| Base64 to literal i64 tables | 2663.530 | 236.566 | retain, 11.259x |
| PC-relative table prototype, skip padding with branch | 263.925 | 267.457 | reject, no gain |
| Four-row expansion | 263.660 | 156.895 | retain, 40.49% reduction |
| Channel expression inside kernel | 135.150 | 117.723 | retain, 12.89% reduction |
| PC-relative prototype, NOP padding without branch | 118.267 | 118.431 | reject, no gain |

Do not multiply gains from separate runs. Only the final three-arm run
supports the 24.597x combined result. The PC-relative prototypes preserve all
byte offsets and checked-index branches and pass the output checks; neither
survives Reflect, so no corresponding compiler change is implemented.

An exploratory loop-carried mutable output handle compiled but native `check`
refused it as nonlinear. The final generator uses a recursive helper with an
explicit updated handle, which both native commands accept. Exploratory
receipts remain separately archived; their timings are not the final result.

The retained candidates satisfy the numerical research diagnostics (at least
5% improvement, gap larger than summed sample SD, relative SD at most 10%).
The repository's formal perfgate launcher still refuses its removed JVM
route. **Formal qualification remains false**, as does official Embench score
status. The six-domain/five-comparator claim is unchanged. i64 tables also
occupy more data bytes than C's signed-byte tables; no size win is claimed.

## Native provenance and reproduction

Compiler: source-built unified Amu generation 3,
`abcc1318957af7d3a09cfd66c06d17821b5cf47f4c47d02b5620e9e92a24f02e`,
6,043,128 bytes, previously reproduced in three byte-identical generations.
The seed/image is unchanged by this research. No Node/nbb/JVM compiler is used.
Python and Clang here are bootstrap measurement/generation tools, not product
dependencies; the PRODUCT dependency inventory is identical before and after.

Upstream commit `09c2ed8c3b7008c95d08b038de4a3f6dc103ed70`, depthconv source SHA256
`a6aadf6e0741922d4b32b8a7821cbea64f9eae00ca8cb8603b1586ec49c94bad`.
The generator refuses any different batch profile. C benchmark_body is
unchanged; the small bridge supplies the same batch count and verifies once.
The batch measurement contract admits positive counts only. It is not a
comparison of the two exports' error handling for invalid counts.

Use a research directory under the comparison root containing `runner`,
`images/r6m`, and `upstream/`. For each arm, generate its source, use the
selfhost compiler to `check` and `compile --target aarch64-macos --output`,
then `extract-native --symbol batch` to `<name>.bin`, recording stdout in
`<name>-extract.log`. Extract `output-channel` to a separate file and record
stdout in `<name>-output-extract.log`. Copy the archived `c-bridge.c` into the
research directory, then run:

```
python3 scripts/seed/image/measure-depthconv-batch.py <research-directory> \
  --baseline base64 --candidate inline --output final-results.json
```

The harness compiles C locally, checks all output channels, calibrates each
arm separately, rotates measurement order, records raw timings and hashes,
and refuses to replace existing results. The final generated source and raw
artifact hashes agree with the receipts.

Evidence: `docs/evidence/coscientist-depthconv-20261004/final-results.json`,
`sha256.json`, and `research-artifacts.tgz` (all exploratory/final sources,
native artifacts, provenance, extraction logs, patches, timing receipts and
final guard/dependency checks). Earlier compiler/runner provenance is recorded
in the seed17 and C-comparison evidence. No full-suite score is updated.
