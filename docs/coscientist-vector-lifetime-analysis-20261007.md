# ベクトル境界解析の研究と反例（2026-10-07）

複数の元Embench入力へ適用するため、ベクトルの長さ・別名・呼び出し・生存期間を解析する規則を設計し、実行可能な診断を作った。まだコンパイラへの適用や性能改善を認定していない。

最初の規則は、全呼び出しと分岐から `0 <= k < length` を証明した定数添字に限り、元の比較命令とハンドル検査を残して分岐・停止命令だけを省く。関数名や入力名による特別扱いをせず、燃料・新しい値の読み出し・書き込み・関数数・フレームを保持する。既存G領域の未使用末尾に有限の解析表を置く案で、初期状態がゼロでない場合、上限超過や証明中断の場合は元の生成へ戻る。[具体的な設計](evidence/coscientist-inverse-aes-20261007/vector-research/implementation-plan-v2.md)は独立レビュー済みだが、実装の添字安全性・中断時消去・再帰不変条件の証明は別途必要。

実際の19本のSIR/FRECを読むドメイン診断では17本が容量条件を通過した。nsichneuとstatemateは関数数・呼び出し辺数の上限で対象外。負の添字、不正な関数範囲、容量超過、非ゼロの解析領域など7つの固定制御を検出した。これは最適化の適用箇所数ではない。5つの重点入力では157箇所の定数添字があり、モード・仮の分岐数条件を加えると静的上限は52箇所だった。実際の呼び出し・再帰・別名・全先行辺の証明がなければ省略しない。

生存期間の有限モデルでは、2つの記述子・長さ1/3・5種類の添字について全到達状態を探索した。領域解放・未知の呼び出し・外部代入で事実を無効化する規則は124状態・620照合で反例0。無効化の省略、未知の呼び出しを信頼する規則、誤った別名規則ではそれぞれ40・40・16の反例を検出した。例えば「長さ3を確保→領域解放→同じ番号で長さ1を確保→添字1」では、ハンドル検査が通っても添字検査は省略できない。このモデルは実際のローダー・全CFG・全メモリの定理証明ではない。

[3ファイルの保存証拠](evidence/coscientist-inverse-aes-20261007/vector-research/README.md)は約1.61MB。親担当も別ディレクトリで再検査し、19本のドメイン診断・7制御・3種の反例を再計算した。ネイティブ・ソルバー・ネットワーク・測定は実行しない。途中の診断修正、初期報告、入力・実装契約のハッシュも残した。進行中の全呼び出し参照解析はこの封印済みパケットに含めていない。

GP2に似た局所的な規則を、型・effect・trap・別名・生存期間の条件付きで適用し、Simpleのような有限の解析とworklistで実行する方針。状態遷移の反例探索と、将来の生成前後の命令・辺の照合を分ける。プログラムのDefCIDと、規則・予算・ランタイム契約を含むビルドの識別も分け、CID一致を意味保存の証明とは呼ばない。

次の判定条件は重点入力3本以上・実際の適用箇所32以上。未達なら負結果を保持し、条件を弱めず原因を調べる。以後は機械コードを変えない型付き解析版、独立した証明情報の照合、分岐省略版の自己再ビルド・機能・低負荷性能の順で進める。全19入力でC以上という目標、製品への採用、公式Embench採点は未達成。

## 全呼び出し参照解析の追補

初期の8ブロック設計で得た17・28・30候補の負結果を保持した上で、V5参照解析を封印した。全19本を再計算し、重点5本ではEDN 4、SHA-256 11、PicoJPEG 30、QRduino 12、XGBoost 3の計60候補を再現した。これは条件付きの参照モデル上の箇所数であり、実際のコンパイラ適用数ではない。モジュール容量の拒否2本を残し、不正な引数数、関数ポインター、未知の呼び出し、別名、循環した根拠など13の否定対照も再現した。

全ての公開・非private・export・関数アドレスの根から閉じた呼び出しグラフを調べる。PicoJPEGの到達しないprivate関数2本は、呼び出し元の不明情報を伝える対象からだけ除く。元の関数・命令は削除しない。未知や容量超過の呼び出し元を無視して肯定的な証明を作らない。

64ブロック×ローカル64＋一時値64×4フィールドを含む33,792ワードを、既存LPの未使用領域に置く設計を独立確認した。現在の肯定的な要約に必要な最大は40ブロック。一方、無関係な一部関数は64ブロックを大幅に超えるため、完全なeffect・呼び出し・関数アドレス走査は維持しつつ、その詳細解析と引数の事実を未知にする。解析中は既存のLP検索処理を呼ばず、成功・拒否・エラー時とも全予約領域をゼロへ戻して通常生成へ進む。

[別の3ファイル証拠パケット](evidence/coscientist-inverse-aes-20261007/vector-reference/README.md)は約1.47MB。親担当が新しいディレクトリで再検査し、19本・60候補・13対照・配置計算に一致した。142の入力目録項目を照合し、ネイティブ実行・ネットワーク・測定は行わない。以前の負結果と初期の引数数診断失敗を保存し、変更中の型付きソースはこの固定証拠に含めていない。

参照解析の転送ステップ以外も含む共通作業予算、型付き添字安全性、領域所有・中断時消去、実際の生成前後比較は未認定。機械コードを変えないKotoba解析版を作成中で、32箇所・3本の判定条件は実際のコンパイラ適用で満たす必要がある。新しい性能値・C超え・製品採用・公式スコアをこの候補数から主張しない。

### 独立レビューで見つかった中断契約の差

封印後の[独立レビュー](evidence/coscientist-inverse-aes-20261007/vector-reference/independent-review/report.json)で、現在の19本の公開入口・関数アドレス・完全な宣言呼び出し辺は一致し、対象解析の収束も確認した。ただし追加の混合診断では、無関係な10関数の別名連鎖が8回の上限に達したとき、別名要約は消去されても、独立した確保からの読み出し候補1つが残った。親担当も同じ反例を再現した。値の誤りや現在の19本への影響は示されていないが、「中断時は全候補を破棄する」という強い契約と異なる。

V5パケットは変更せず、この反例とレビューの初期構文失敗を別に保存する。後続の参照解析とKotoba版では全体拒否を適用し、この混合診断を追加の制御にする。独立した再検査が完了するまで修正済みとは呼ばない。型付き下書きの資源レビューでも、極端なi64添字から必要量を計算するときの加算オーバーフローと、非関数定義の予約SIR読み出しを指摘した。有限のオペランド範囲を計算より先に確認し、非関数定義を分けて扱う修正中で、ネイティブビルドには進めていない。

V6を別工程として作成し、親担当も3つの診断ソースを別ディレクトリで実行した。19本の結果はV5とバイト一致し、旧13制御を保持した14制御が通過。混合診断の残存候補は0になった。[V6の記録](evidence/coscientist-inverse-aes-20261007/vector-reference/v6/README.md)を追加し、元のV5反例は保持した。別名解析の中断は実際に制御で強制したが、呼び出し境界解析の中断処理はソースレビューのみで、別の追加制御では強制していない。V6の記録はローカル入力を参照するため、新たな単独3ファイルパケットとは呼ばない。

[型付き下書きの資源レビュー](evidence/coscientist-inverse-aes-20261007/vector-reference/typed-draft-resource-review/report.json)も否定結果として保存した。オペランド計算前の範囲確認、非関数定義、G領域所有の検査、上限対象の作業と必須消去の区別、全候補破棄の5項目を修正・再検査する必要がある。保存ソースは問題が見つかった下書きであり、製品への適用やネイティブ資格を示さない。
